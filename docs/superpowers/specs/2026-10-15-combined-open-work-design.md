# Combined Open Work

## Intent and authorization
The user requested a view of all their open work across Jira instances, clarified **only issues assigned to the user**, and approved a combined view with selectable saved sites, a source-site column, unchanged active site, and independent site failures. This is a bounded read-only feature following the existing React/Express patterns. It is separate from refactor PR34, based on its branch tip110c3e4.

## Behavior
Add **Combined Open Work** to the main navigation at `/combined-open-work`. Load enabled saved Jira entries and select all by default. The user chooses one or more entries and explicitly clicks **Load open work**; after a result the button may say **Refresh**. The page explains it shows issues assigned to the account configured for each site. Never switch the active Jira site to collect results.

Builder calls: open means `statusCategory != Done`, matching the current export/planning convention; identity is Jira `currentUser()` evaluated independently for each saved site's captured email/token. Use fixed JQL `assignee = currentUser() AND statusCategory != Done ORDER BY updated DESC, key ASC`. No arbitrary JQL, account selector or project restriction is accepted. This finds the user's work across projects on each selected site, including projects absent from presets.

Render one combined read-only table: **Jira site**, **Issue**, **Title**, **Status**, **Jira priority**, **Due date**. Site label and hostname are visible; issue links are constructed from the validated HTTPS origin plus encoded issue key, never a Jira-supplied URL. Use the existing UI styles and readable date-only values. This initial view does not add edits, local/Team metadata, comments, exports, extra filter systems, automatic polling, or personal To Do rows. Existing site-specific editing stays as it is. Selecting new sites clears the old result so it cannot be mistaken for the new selection. Show fetched time, returned count, loading/cancel, empty, no-selection and no-saved-sites states, with a Settings link for the last case. A failed site is visibly failed, never reported as zero work. Successful rows remain visible alongside failed/partial site notices. Users can refresh/retry the selected set.

Saved entries are identities even if hostname or issue key repeats. Keep distinct `(instanceId,siteHost,issueKey)` rows and labels, deduplicating repeated issue keys only within one saved entry. All output is plain React text. Refresh, selection change and unmount abort the obsolete request; a late response must never replace newer state.

## Boundaries and collection
Reuse `listInstances`, `getInstanceCredentials`, `beginInstanceOperations`, `requestJira`, and `searchAllIssues`. A short new collector handles only this view; do not call the workbook preview collector or duplicate transport/search/registry implementations. Collection captures each selected entry's credentials once and leases selected registry entries so edits/deletion cannot invalidate it. Active-site switches remain independent. Release only after all selected requests settle, including cancellation/failure siblings. Use no active-site DB reads, migrations, writes, credential returns or new dependency/class.

Reuse pagination, including opaque next tokens and explicit completeness. Builder calls: `DOCKET_OPEN_WORK_MAX_ROWS_PER_SITE` defaults5000, capped5000; `DOCKET_OPEN_WORK_TIMEOUT_MS` defaults120000, capped600000 (positive integers, invalid values use default). Request transport retains existing Jira deadline. One finite collection deadline includes fetch/body work. Max5 enabled entries uses existing `MAX_JIRA_INSTANCES`. For a row/deadline/pagination limit show the site's returned rows as **partial** with a clear warning that the list is incomplete. Never label a capped/interrupted list complete, even without Jira total. Other site errors can show failed/no rows; do not silently claim successful zero work. Caller cancellation aborts real transport, awaits settlement, then sends no stale response. Configuration/unapproved-host/auth/rate/network errors use safe per-site messages; raw upstream errors/credentials are not exposed. Unselected sites are never requested. No token or PII fixtures/logs.

## API contract
`POST /api/combined-open-work` accepts only `{instanceIds: string[]}`: one to five unique nonempty IDs of enabled saved entries. Unknown/disabled/duplicate/extra fields =>400 before outbound work. Host validation is per selected site so one old blocked hostname does not hide successful peers.

Response `{fetchedAt: ISOtimestamp, sites:[{instanceId,displayName,siteHost,status,rows,loaded,message?}]}`; status is `complete|partial|failed`; rows are `{issueKey,summary,status,jiraPriority,dueDate,url}` with optional/missing Jira text represented as empty string, dueDate string or null. `loaded` is deduplicated returned rows. Empty COMPLETE is distinct from FAILED. Unsafe/malformed issue identity must not produce a link; report that site failed rather than invent a key. No response token/email/assignee personal details. `siteHost` may be empty for an invalid saved URL.

The route is outside active-site lease wrapping, under the existing Host/Origin policy. It uses an AbortController tied to request/response disconnection and `Cache-Control:no-store`. The client uses `requestJsonNow` like workbook export: this is a read operation and must not register a siteSave job or acquire an active-site header dependency.

## Validation and limits
Cover same key/site duplicates, A/B credentials, no active-state mutation, requests only selected entries, currentUser/open JQL and minimal fields, multi-page results, one-site failure, all-site failure, blocked host, missing token, bounds/partial data, malformed pages/keys, cancellation with delayed settlement and registry release. Client tests cover selection, read-only queue classification, empty/error/partial results, row links/labels, refresh and stale response suppression. Synthetic browser smoke uses copied config/fake upstream and new temporary tab; no real `.env`, live Jira or user database. Full unit/build checks after implementation; no SQL schema/DB integration changes expected. Company Sonar gate remains external because its source-upload destination was not approved; do not retry/bypass it. Native company/live Jira validation is not claimed.
